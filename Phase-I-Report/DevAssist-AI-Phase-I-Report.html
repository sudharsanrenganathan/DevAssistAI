Abstract

Modern software development is fragmented across a large number of disconnected tools. A student or an early-career developer typically moves between a conversational assistant for general questions, a separate service to query private documents, another to review code, an online compiler to run it, a competitive-programming judge to practise on, and yet another generator to scaffold new projects. Each of these tools maintains its own account, its own interface conventions and its own copy of the user's data, and none of them shares context with the others. The cost of this fragmentation is paid in context switching, in duplicated effort, and in a loss of privacy whenever private material is uploaded to an unrelated third-party service.

DevAssist AI is a unified, web-based developer assistance platform that consolidates seven such capabilities behind a single authenticated account and a single design system. The platform provides: Global AI, a general-purpose streaming chat assistant with persistent, searchable history; Secret AI, a private document question-answering module in which answers are grounded strictly in documents the user has uploaded; Code Analyzer, which returns structured defect reports, an optimised rewrite and a time-complexity comparison; Online Compiler, a zero-setup multi-language execution environment; VoidMain, a competitive-programming judge with problem set, verdicts and leaderboard; Ignite, an AI project builder that generates a complete multi-file frontend project from a single natural-language prompt; and Circuit, which converts a question into a validated, animatable step-by-step visual explanation.

The system is implemented as three independently deployed services: a framework-free HTML/CSS/JavaScript frontend, a Spring Boot 3 backend written in Java following a layered clean architecture, and a Python FastAPI inference engine. Persistence and authentication are provided by a managed PostgreSQL instance, with every stored row keyed to the owning user's universally unique identifier so that multi-tenant isolation is enforced uniformly across all seven modules. Large-language-model access is routed through a provider-abstraction registry that allows the active vendor and model to be changed by editing a single environment variable, with no code change and no redeployment of application logic.

A distinguishing engineering constraint of this work is that the entire platform runs on free-tier infrastructure. Meeting that constraint required a set of deliberate mitigations that are documented and evaluated in this report: a scheduled keep-alive service that suppresses cold starts, lazy importing of heavy machine-learning dependencies, per-user sliding-window rate limiting, a daily token-accounting ledger, sequential generation with exponential backoff, and a context-injection strategy for document grounding that avoids loading embedding models into a memory-constrained container. Phase I delivers a fully functional deployed system covering all seven modules; Phase II will address persistent vector storage, backend code generation and formal quantitative benchmarking.

Keywords: Large Language Models, Retrieval-Augmented Generation, Developer Tools, Microservices, Multi-Tenant Isolation, Cloud Computing, Automated Code Analysis.

CHAPTER 1INTRODUCTION

1.1  Overview

The practice of software development has been reshaped over the last few years by large language models. Tasks that previously demanded either an experienced colleague or a long search through documentation — explaining an unfamiliar error, reviewing a function for correctness, summarising a specification, drafting a first version of a module — can now be addressed conversationally. The benefit, however, has arrived in a fragmented form. Each capability is delivered by a different vendor, behind a different account, with a different interface and a different privacy policy.

DevAssist AI is a unified web platform that consolidates seven distinct developer assistance capabilities behind one authenticated account and one coherent interface. It is aimed primarily at engineering students and early-career developers, for whom the cost of assembling and paying for a toolchain is a real barrier. The platform is deployed publicly and operates entirely on free-tier cloud infrastructure, which makes the engineering of the system, and not merely its feature list, a substantive part of the contribution.

1.2  Motivation and Problem Statement

Three specific problems motivated this work. The first is tool fragmentation. A student debugging an assignment may consult a chat assistant, paste the same code into a separate analysis service, run it on a third online compiler, and practise the underlying concept on a fourth competitive-programming site. No context is carried between them, and the same information is re-entered repeatedly.

The second is privacy of private material. Asking questions about a personal document normally means uploading it to a general-purpose service whose retention behaviour is opaque, and whose answers may be influenced by material entirely outside that document.

The third is cost. Commercial assistants, managed vector databases and hosted execution sandboxes are individually inexpensive but collectively out of reach for a student. The problem addressed by this project is therefore to design and build a single, secure, multi-tenant platform that delivers these capabilities together, grounds private queries strictly in user-owned data, and sustains acceptable behaviour under the hard resource limits of free-tier hosting.

1

1.3  Objectives

The objectives of Phase I of this project are stated below.

  1. To design a three-tier, service-oriented architecture in which the presentation, business and inference concerns are independently deployable and independently replaceable.
  2. To implement seven functional modules — Global AI, Secret AI, Code Analyzer, Online Compiler, VoidMain, Ignite and Circuit — behind a single authenticated session.
  3. To enforce strict multi-tenant data isolation, so that every persisted record is bound to the universally unique identifier of its owner and no endpoint can return another user's data.
  4. To ground private document question-answering exclusively in material the user has uploaded, so that no external corpus contributes to the answer.
  5. To abstract large-language-model access behind a provider registry, so that the active vendor and model can be changed through configuration alone, without modifying application code.
  6. To design and evaluate mitigations that allow the platform to operate acceptably within free-tier constraints on memory, request duration, request rate and token quota.
  7. To validate the behaviour of the inference and orchestration layers through an automated test suite in which all external model providers are mocked.

1.4  Scope of the Project

The scope of Phase I covers the complete design, implementation and public deployment of the seven modules listed above, together with authentication, per-user persistence, request rate limiting and token accounting. Code execution is delegated to an external sandboxing service, and model inference is delegated to external providers; the project does not train or fine-tune any model of its own.

The following are explicitly outside the scope of this phase: generation of backend or database code by the Ignite module, which currently produces frontend projects only; a persistent vector store, since document context is presently held in process memory; real-time collaborative editing; and native mobile applications. These are treated as Phase II objectives and are set out in Chapter 6.

CHAPTER 2LITERATURE SURVEY

2.1  Introduction

DevAssist AI draws on six established lines of work: the transformer architecture and the instruction-following models built upon it, retrieval-augmented generation, automated code analysis and synthesis, sandboxed remote code execution, automated judging of competitive programming submissions, and the architectural patterns used to compose these into a secure multi-tenant service. This chapter reviews each line for the technique it contributes and for the limitation it leaves open.

2.2  Review of Existing Work

1. Transformer architecture. Vaswani et al. [1] introduced the transformer, replacing recurrence with self-attention and making it practical to train models on very large corpora. Every model used by this platform descends from that architecture. The work is foundational rather than applied: it establishes the capability but says nothing about how such a model should be exposed to an end user, budgeted, or restricted to a private data set.

2. Few-shot instruction following. Brown et al. [2] demonstrated that a sufficiently large language model performs new tasks from a natural-language description and a handful of examples, without gradient updates. This result is what allows a single deployed model in DevAssist AI to serve seven functionally different modules through prompt construction alone. The limitation is reliability: the same property that makes the model general also makes its output format unstable, which the present work addresses by validating every structured response against a schema before it reaches the user interface.

3. Code-trained models. Chen et al. [3] evaluated models trained specifically on public source code and reported both strong functional synthesis and a persistent rate of subtly incorrect output. Their finding directly informs the design of the Code Analyzer module in this project, which presents an optimised rewrite alongside the original in a difference view rather than substituting it silently, leaving the developer as the final reviewer.

4

4. Retrieval-augmented generation. Lewis et al. [4] combined a parametric generator with a non-parametric retriever, so that answers are conditioned on documents fetched at inference time. This is the technique underlying the Secret AI module. Their formulation assumes a retrieval index that can be held in memory; the present work departs from this assumption because the deployment target cannot host an embedding model, and adopts a direct context-injection strategy instead, as described in Section 4.3.

5. Sparse and dense retrieval. Robertson and Zaragoza [21] formalised Okapi BM25, a probabilistic term-weighting ranker that needs only term statistics and remains a strong baseline for passage retrieval. Karpukhin et al. [5] later showed that dense retrieval with a dual encoder outperforms sparse matching on open-domain questions, and Reimers and Gurevych [6] made such encoders practical through comparable sentence embeddings. This project adopts the sparse method: BM25 needs no resident model, which is decisive under a 512 MB ceiling.

6. Efficient similarity search. Johnson et al. [7] presented FAISS, a library for billion-scale approximate nearest-neighbour search. A FAISS-backed vector store is implemented in this project and is used in local execution, but it is not active in the deployed configuration because loading the accompanying embedding model exceeds the memory ceiling of the free-tier container. This trade-off is reported honestly in Section 4.3 rather than concealed.

7. Program synthesis from natural language. Austin et al. [8] studied the generation of complete programs from natural-language descriptions and observed that success degrades sharply as the required output grows. The Ignite module responds to this finding structurally: rather than requesting an entire project in one call, it first obtains a file-level plan and then generates each file in a separate call, so that a failure is isolated to one file and can be retried independently.

8. Remote execution sandboxes and online judges. Public compilation services such as Wandbox [15] and open-source judging systems such as Judge0 [14] establish the accepted pattern for executing untrusted user code: isolate it in a disposable container outside the application process. Both the Online Compiler and the VoidMain judge in this project follow this pattern by delegating execution to an external sandbox, so that no user-supplied code ever runs on the application servers.

9. Architecture and authentication. Fielding [13] defined the REST constraints that govern the interfaces between the three services here; Martin [11] and Newman [12] set out the layering and service-decomposition rules the backend follows; and RFC 7519 [9] and RFC 6749 [10] define the token and delegated-authorisation mechanisms used to carry identity from the browser to every protected endpoint.

2.4  Research Gap and Inference

The review shows that each individual capability required by this project is well established in isolation. Conversational assistance, grounded question answering, code analysis, sandboxed execution, automated judging and program synthesis all have mature reference implementations. What the literature does not address is their integration under a single tenancy model, and their operation under severe resource constraints.

Two gaps follow. First, no reviewed system offers these capabilities together with a uniform isolation guarantee binding a user's documents, conversations, submissions and generated projects to one identity. Second, the reviewed retrieval techniques presuppose infrastructure — resident embedding models, persistent indices, long-running processes — that free-tier hosting does not provide, and the literature offers little guidance when that presupposition fails.

DevAssist AI addresses the first with a single identifier applied uniformly across every entity in the schema, and the second with an explicit set of mitigations: keep-alive scheduling, lazy importing, sliding-window rate limiting, daily token accounting and bounded context injection.

CHAPTER 3AIM AND SCOPE OF THE PRESENT INVESTIGATION

3.1  Aim of the Project

The aim of this project is to design, implement and publicly deploy a unified, secure, multi-tenant developer assistance platform that delivers seven distinct AI-assisted capabilities behind a single authenticated account, grounds all private document queries strictly in user-owned material, decouples the system from any single model vendor through a configuration-level provider abstraction, and sustains acceptable behaviour entirely within the resource limits of free-tier cloud infrastructure.

3.2  Existing System

The existing practice is not a single system but a habitual assembly of unrelated services: a commercial assistant for general questions, a separate service for private documents, an editor plugin or static analyser for code review, a public online compiler, a competitive-programming site for practice, and a scaffolding generator for new projects.

Each authenticates the user separately, keeps its own copy of whatever is submitted, and imposes its own conventions. Nothing is shared: a document uploaded to one is invisible to another, and a conversation held in one cannot inform an analysis in the next.

3.3  Limitations of the Existing System

  1. Context loss across tools. Information is re-entered at every boundary, and reasoning established in one tool is unavailable to the next.
  2. Uncontrolled exposure of private material. Documents go to services whose retention policies are opaque, and answers may be shaped by material outside the document.
  3. Cumulative cost. Individually modest subscriptions become collectively prohibitive for a student, and their free tiers are too restricted for sustained use.
  4. Vendor lock-in. Each service is bound to one provider, so an outage or price change cannot be absorbed by the user.
  5. No unified isolation guarantee. With data scattered across providers there is no single, auditable statement of who can access what.
  6. Inconsistent interaction model. Seven interfaces impose seven sets of conventions, raising the learning cost.
7

3.4  Proposed System

The proposed system is a single web platform, accessed through one authenticated session, that exposes seven modules over a common design system and a common persistence layer. Its defining properties are as follows.

  1. Unified tenancy. Every persisted entity carries the universally unique identifier of its owner and every read path filters on it, so isolation is a property of the schema rather than of individual endpoint code.
  2. Strict grounding for private data. The model is supplied only with text extracted from the document the user selected; no external corpus can contribute to the answer.
  3. Provider independence. Model access is resolved at request time through a registry keyed by an environment variable. Changing vendor is a configuration change; adding one is a single class and a single registry entry.
  4. Delegated execution. User-supplied code never runs on the application servers. It is dispatched to an external sandbox and only its output is returned.
  5. Explicit resource governance. A per-user sliding-window rate limiter and a daily token ledger bound consumption before any request reaches a quota-limited provider.
  6. Free-tier operability. A keep-alive scheduler suppresses cold starts, heavy libraries are imported lazily, and generation is sequential with backoff so request duration stays within platform timeouts.

3.5  Feasibility Study

Technical feasibility. Every component rests on mature, documented technology: Spring Boot for the service layer, FastAPI for inference orchestration, managed PostgreSQL for persistence and vendor-hosted models over HTTP. No component required an unproven capability, and the complete system has been deployed and exercised end to end.

Economic feasibility. Recurring infrastructure cost is zero. Static hosting, both application services, the database, authentication, storage and inference are all obtained on free tiers, so the cost of the project is development effort alone.

Operational feasibility. The interface follows conventions users already hold from mainstream chat and editor applications, so adoption needs no training. Administration is limited to environment configuration, and provider failure is recoverable by one variable change.

CHAPTER 4SYSTEM DESIGN AND METHODOLOGY

4.1  System Architecture

DevAssist AI is organised as three independently deployed tiers. The presentation tier is a set of static documents served from a content delivery network; it holds no secret and performs no privileged operation. The application tier is a Spring Boot service that owns identity verification, authorisation, persistence and rate limiting. The inference tier is a FastAPI service that owns prompt construction, provider selection, response validation and token accounting. Separating the last two matters: the Java service is stable and transactional, whereas the Python service changes whenever a prompt or a model changes, and the two therefore have very different release rhythms.

The browser never contacts the inference tier or any model vendor directly. Every request carries a signed token, is verified by a servlet filter in the application tier, and is only then proxied inward. This single ingress point is what makes the isolation guarantee auditable: there is exactly one place where identity is established, and every downstream call inherits it.

4.2  Module Design

The platform is decomposed into seven functional modules. Each owns its own routes, its own entities and its own prompt strategy, but all share the same authentication filter, the same persistence layer and the same provider abstraction. Table 4.1 summarises the responsibility and the principal design decision of each.

Module Responsibility Principal Design Decision
Global AI General-purpose conversational assistance with persistent, searchable, pinnable threads. Responses are streamed token by token so that first output appears early; history is stored relationally as threads and messages rather than as opaque blobs, which makes search and per-thread deletion straightforward.
Secret AI Question answering restricted to documents the user has uploaded. Extracted text is bounded and cached per document under a lock; the model receives only that text, so no external corpus can influence the answer. Chunk-level BM25 retrieval is the approved successor (Section 6.3).
Code Analyzer Structured review of submitted source code. A deterministic pattern pre-pass produces optimisation hints that are appended to the prompt, so the model is guided rather than trusted blindly; the rewrite is shown in a difference view, never applied silently.
Online Compiler Multi-language edit, compile and execute with standard input support. Execution is delegated to an external sandbox; no user code runs in the application process.
VoidMain Competitive-programming judge with problem set, verdicts, history and leaderboard. Submissions are executed through the same sandbox and compared against expected output; verdicts and rankings are persisted per identity.
Ignite Generation of a complete multi-file frontend project from one prompt. A planning call returns a file list, after which each file is generated in its own streamed call; failure is isolated to a single file and retried with backoff.
Circuit Step-by-step animated visual explanation of a concept or algorithm. The model returns strict JSON only, validated against a schema with one corrective retry; the interface, not the model, renders the animation.
Table 4.1 – Module responsibilities and design decisions

Two cross-cutting services support all seven. RateLimitService maintains an in-memory sliding window per identity and rejects requests that exceed the configured hourly allowance before any provider is contacted. KeepAliveService issues a scheduled request to the inference tier every fourteen minutes, which keeps the container resident and removes the multi-second cold start that would otherwise precede the first request after a period of inactivity.

4.3  Document Grounding Pipeline

The Secret AI module answers questions about a document without consulting anything outside it. The canonical retrieval-augmented design [4] would embed the document into chunks, index them, and retrieve the nearest neighbours of the question. That design is implemented in this project, but it is not the deployed configuration: loading a sentence-embedding model together with a vector index exceeds the memory ceiling of the free-tier container, and the resulting cold start exceeded the platform request timeout. The deployed pipeline therefore substitutes bounded context injection for retrieval, as shown in Fig. 4.2.

Extracted text is truncated to a fixed budget of thirty thousand characters and held in a per-document cache guarded by a lock, so that concurrent questions neither re-extract the document nor corrupt the shared map. The successor design has been specified and approved: an Okapi BM25 index [21] over paragraph-aware chunks, returning the six highest-scoring chunks per question reassembled in document order. BM25 was chosen over a return to embeddings precisely because it adds no compiled dependency and no resident model, and so fits the memory ceiling that defeated the vector pipeline. It is design, not Phase I result, and is set out in Section 6.3.

4.4  Provider Abstraction and Failover

All model access passes through a registry of provider classes that satisfy a common generation contract. The active provider is resolved per request from an environment variable, and each provider reads its own model identifier from its own variable. Switching vendor is therefore a configuration change with no code modification, and adding a vendor is one class plus one registry entry. Every provider implements three retries with exponential backoff and distinguishes a rate-limit condition, which is retryable, from a client error such as an invalid key, which is not.

This abstraction was validated in practice. When the primary provider's queue backed up and requests began exceeding the read timeout, service was restored by changing a single variable to the alternate provider, with no code change and no redeployment.

4.7  Database Design and Isolation

The schema is deliberately simple. A single users table carries the identity issued by the authentication provider, and every other table stores that same universally unique identifier as a foreign key. Because isolation is expressed once, in the shape of the data, no endpoint can accidentally omit it without the omission being visible in the query itself.

5.2  Module Implementation

The backend observes strict layer boundaries. Controllers validate input and return a response entity; they hold no business logic and make no repository call. Services hold the business logic and own transaction boundaries. Repositories are Spring Data interfaces, so no structured query language appears in the service layer. Dependencies are supplied through constructors rather than field injection, which keeps them explicit and makes every service testable with mocked collaborators. Data transfer objects are Java records.

In the inference tier, all model access is funnelled through a single generation wrapper, so that budget checking and usage recording apply uniformly and cannot be bypassed by a new route. Shared in-process state — the document cache and the two conversation history maps — is accessed only under its corresponding lock, because the server handles concurrent requests in a thread pool. Heavy scientific libraries are imported inside the function that needs them rather than at module scope, which keeps the cold-start time of the container within the platform's request timeout.

Two implementation details are worth recording. First, the Ignite module never asks for an entire project in one request: a planning call returns a strict file list, and each file is then produced in its own streamed call, so a rate-limit rejection costs one file rather than the whole project. Second, the Circuit module accepts only strict JSON from the model, validates it against a schema, and permits exactly one corrective retry before returning a friendly error — the browser, never the model, renders the resulting animation.

Three results are worth discussing. Isolation held under test. With two accounts exercised in parallel, no listing endpoint returned a record belonging to the other identity, which supports expressing isolation in the schema rather than in endpoint code. Provider abstraction proved its value in production. When the primary vendor's queue backed up and read timeouts appeared, service was restored by changing one environment variable; no code was altered. The free-tier mitigations are necessary, not decorative. Without keep-alive scheduling the first request after an idle period incurred a multi-second cold start; without lazy importing the container exceeded its memory ceiling at startup; and without per-file generation, a single rate-limit rejection failed the whole project.

CHAPTER 6CONCLUSION AND FUTURE WORK

6.1  Conclusion

Phase I has delivered a working, publicly deployed platform consolidating seven AI-assisted developer capabilities behind a single authenticated account. The three-tier design separates a static presentation layer, a transactional Java application layer and a Python inference layer, so the component with the fastest rate of change — prompts and model selection — can be revised without disturbing the components that hold user data.

Two decisions proved more valuable than anticipated. Expressing multi-tenant isolation in the schema made the guarantee uniform across all seven modules and removed the possibility of an endpoint quietly omitting it. Routing every model call through a provider registry allowed a real vendor degradation to be absorbed by one configuration change. More broadly, the obstacles to running a multi-service platform on free infrastructure proved addressable by design rather than by expenditure.

6.2  Limitations

Four limitations are acknowledged. Secret AI performs no retrieval. It truncates the document at thirty thousand characters and sends that text whole, so content beyond roughly the first twelve pages is invisible to the model, and every question spends prompt budget on largely irrelevant text. Document context is also held in process memory and is lost when the inference container restarts, which on a free tier is frequent. Ignite generates frontend projects only. Finally, the results in Chapter 5 are observational; no controlled benchmark has yet been run.

6.3  Future Work

The first item, already specified and approved, is real chunk-level retrieval for Secret AI. The document will be split by a paragraph-aware splitter into chunks of about nine hundred characters with a hundred and fifty of overlap, indexed with Okapi BM25 [21], and queried per question for the six best chunks, which are reassembled in document order so the context reads coherently. Short documents bypass retrieval entirely, and any retriever error falls back to the present full-text mode, so the change cannot make the feature worse. BM25 is deliberate rather than expedient: embeddings were tried first and removed after they exhausted the memory of the free-tier container, whereas BM25 is pure Python over a dependency already installed. The measured reduction in prompt tokens and the change in answer accuracy will be recorded.

Beyond that: hybrid lexical and semantic retrieval once paid infrastructure is available; Ignite extended to server and schema code; quota exhaustion surfaced as an explicit message rather than a silent failure; responsive layouts; a larger problem set with a contest mode; and a formal evaluation of latency per provider, generation time against project size and tokens per module.
